# GPU는 왜 병렬 연산에 강한가 — CPU와의 구조 차이와 SIMT 실행 모델

_written by Claude-Code_

## 배경: 작전명 AI, 코드네임 23 — 세번째 미션

[[semiconductor-chip-types-and-gpgpu|이전 미션]]에서 반도체 칩을 메모리반도체와 시스템반도체로 나누고, GPU가 그래픽 처리를 넘어 범용 연산에 쓰이는 GPGPU라는 개념까지 훑었다. 그런데 정작 GPU 안에서 무슨 일이 일어나길래 "병렬 연산에 강하다"는 말이 나오는지는 짚고 넘어가지 못했다. 코어가 많다는 것은 알겠는데, 많으면 왜 빠른지, 코어 수천 개를 어떻게 관리하는지는 다른 문제다.

세번째 미션은 여기서 시작한다. CPU와 GPU가 같은 시스템반도체이면서도 왜 이렇게 다른 방향으로 진화했는지, 그 차이가 다이(die) 위에서 어떻게 드러나는지, 그리고 GPU가 수천 개의 코어를 다루기 위해 고안한 SIMT 실행 모델과 워프, 메모리 계층까지 정리한다.

---

## CPU와 GPU, 같은 시스템반도체인데 왜 이렇게 다른가

CPU와 GPU는 둘 다 연산을 담당하는 시스템반도체다. 하지만 다이 면적을 어디에 쓰느냐가 완전히 다르다. CPU는 다이 면적 대부분을 제어 로직(Control)과 캐시(Cache)에 쓰고, 실제 연산을 담당하는 ALU는 상대적으로 작은 비중을 차지한다. GPU는 정반대다. 제어 로직과 캐시는 최소화하고, 다이 면적 대부분을 ALU로 채운다.

```
CPU 다이 구성(개념도)
┌───────────────────────────────────────┐
│ Control(제어 로직)   ████████          │  분기 예측, 비순차 실행
│ Cache(L1/L2/L3)      ████████████████  │  크고 다단계
│ ALU(연산 유닛)       ████              │  적은 코어, 강력한 단일 스레드
└───────────────────────────────────────┘

GPU 다이 구성(개념도)
┌───────────────────────────────────────┐
│ Control(제어 로직)   ██                │  코어 묶음이 로직 하나를 공유
│ Cache                ████              │  작음
│ ALU(연산 유닛)       ████████████████████████████  │  수천 개의 단순한 코어
└───────────────────────────────────────┘
```

CPU 코어 하나는 분기 예측(Branch Prediction), 비순차 실행(Out-of-Order Execution), 큰 캐시 같은 장치를 동원해 복잡한 로직을 빠르게 처리하도록 설계된다. 코어 수는 수 개에서 수십 개에 그치지만, 코어 하나하나의 단일 스레드 성능은 GPU 코어와 비교가 안 될 만큼 강력하다.

GPU 코어(CUDA 코어라고도 부른다)는 반대다. 분기 예측도, 비순차 실행도 없다. 코어 하나는 단순한 산술 연산만 반복한다. 대신 이런 단순한 코어를 수천 개씩 박아 넣는다. 코어 하나의 성능은 CPU 코어에 비할 바가 아니지만, 동일한 연산을 수천 개의 데이터에 동시에 적용해야 하는 작업에서는 이 단순함과 개수가 압도적인 처리량으로 돌아온다.

| 구분 | CPU | GPU |
|------|-----|-----|
| 다이 면적 비중 | Control·Cache 위주 | ALU 위주 |
| 코어 수 | 수 개 ~ 수십 개 | 수천 개 |
| 코어 하나의 성능 | 강력함(분기 예측, OoO 실행) | 단순함 |
| 캐시 | 크고 다단계(L1/L2/L3) | 작음, 공유 자원 |
| 강점 | 복잡한 제어 흐름, 순차 처리 | 동일 연산의 대량 병렬 처리 |
| 설계 목표 | 지연시간(Latency) 최소화 | 처리량(Throughput) 극대화 |

이 마지막 줄이 핵심이다. CPU는 작업 하나를 최대한 빨리 끝내는 데(지연시간 최소화) 최적화되어 있고, GPU는 작업 전체를 최대한 많이 동시에 끝내는 데(처리량 극대화) 최적화되어 있다. 목표가 다르니 다이 위의 설계도 다르게 그려진 것뿐이다.

## SIMD와 SIMT — 명령어 하나로 수천 개의 스레드를 다룬다

코어를 수천 개 늘어놓았다고 저절로 빨라지는 건 아니다. 코어 수천 개에 각각 다른 명령어를 독립적으로 실행시키려면 코어마다 별도의 제어 로직(명령어 디코더, 스케줄러)이 필요한데, 그러면 다이 면적이 다시 제어 로직으로 잠식된다. GPU가 택한 해법은 코어 여러 개를 묶어 하나의 명령어를 동시에 실행시키는 것이다. 이 실행 모델이 SIMD와 SIMT다.

**SIMD(Single Instruction, Multiple Data)**는 명령어 하나로 여러 데이터를 동시에 처리하는 방식이다. CPU도 SSE, AVX 같은 명령어 집합으로 SIMD를 지원한다. 배열 원소 8개를 한 번에 더하는 연산을 명령어 하나로 처리하는 식이다.

GPU는 여기서 한 걸음 더 나간 **SIMT(Single Instruction, Multiple Thread)** 모델을 쓴다. SIMD가 "명령어 하나 + 데이터 여러 개"라면, SIMT는 "명령어 하나 + 스레드 여러 개"다. 겉보기엔 비슷하지만 관점이 다르다. SIMT에서는 스레드 하나하나가 독립된 실행 흐름을 가진 것처럼 프로그래밍하고, 하드웨어가 그 스레드들을 묶어 같은 명령어를 동시에 실행시킨다. 개발자는 스레드 단위로 코드를 짜지만, 실제로는 스레드 묶음이 한 몸처럼 움직인다.

이 묶음의 크기가 **워프(Warp)**다. NVIDIA GPU에서 워프는 32개의 스레드로 구성된다. 워프 안의 32개 스레드는 항상 같은 명령어를 같은 사이클에 실행한다. 이것이 락스텝(lockstep) 실행이다.

### 분기가 갈리면 무슨 일이 일어나나

워프 안의 32개 스레드가 `if (조건)` 같은 분기문을 만났는데 스레드마다 조건 결과가 다르면 문제가 생긴다. 워프는 한 사이클에 하나의 명령어만 실행할 수 있으므로, 조건이 참인 스레드들을 먼저 실행하고 거짓인 스레드는 대기시킨 다음, 다시 거짓 분기를 실행하고 참인 스레드를 대기시킨다. 두 경로를 순차적으로 다 실행하는 것이다. 이를 **워프 분기(Warp Divergence)**라 부른다. 분기가 갈릴수록 워프의 실질 처리량은 갈라진 경로 수만큼 줄어든다. GPU 코드를 짤 때 조건문을 최소화하라는 조언이 나오는 이유가 여기에 있다.

## 워프와 스레드 블록 — GPU가 일을 나누는 단위

워프가 GPU 하드웨어가 실제로 실행하는 단위라면, 개발자가 코드를 작성할 때 다루는 단위는 그보다 한 층 위에 있다. CUDA를 기준으로 실행 계층은 다음과 같이 쌓인다.

```
그리드(Grid)
 └─ 스레드 블록(Thread Block) 여러 개
     └─ 워프(Warp, 32개 스레드 단위) 여러 개
         └─ 스레드(Thread) 하나
```

- **스레드(Thread)**: 가장 작은 실행 단위. 스레드 하나가 데이터 하나를 처리한다.
- **스레드 블록(Thread Block)**: 스레드를 묶은 그룹. 같은 블록에 속한 스레드는 하나의 SM(Streaming Multiprocessor, GPU 내부의 연산 코어 묶음) 위에서 실행되며, 공유 메모리와 동기화 지점(barrier)을 함께 쓸 수 있다.
- **워프(Warp)**: 스레드 블록을 하드웨어가 32개씩 잘라 실제로 스케줄링하는 단위.
- **그리드(Grid)**: 스레드 블록 전체의 묶음. 커널(kernel, GPU에서 실행되는 함수) 하나를 실행할 때 그리드 하나가 만들어진다.

개발자는 "이 연산을 스레드 100만 개로 나눠서 처리해라" 정도만 지정하면 된다. 그 100만 개를 몇 개의 블록으로 쪼개고, 각 블록을 어느 SM에 배치하고, 블록 안의 스레드를 32개씩 워프로 묶어 스케줄링하는 일은 GPU 하드웨어와 드라이버가 맡는다. 개발자 입장에서는 스레드 단위로 사고하고, 하드웨어 입장에서는 워프 단위로 실행한다. 이 두 관점의 간극을 메우는 게 SIMT 모델이다.

## GPU 내부 물리적 구조 — Command Processor, GPC, TPC, SM

앞서 워프와 스레드 블록은 개발자와 하드웨어가 스레드를 다루는 논리적 단위였다. 이 논리적 단위가 실제 다이 위에서 어떤 물리적 회로에 배치되는지를 봐야 그림이 완성된다.

![GPU 내부 구조와 VGA(외장 그래픽) vs 내장 그래픽(iGPU) 구조 비교|800](/assets/posts/cs/gpu-architecture-simt-execution-model/gpu-architecture-overview.png)

GPU 다이는 위에서 아래로 다음과 같이 쌓인다.

```
GPU
 └─ Command Processor / Front End   명령 수신, 파싱, 스케줄링
     └─ GPC (Graphics Processing Cluster)  여러 개
         └─ TPC (Texture Processing Cluster)  여러 개
             └─ SM (Streaming Multiprocessor)  여러 개
 └─ L2 Cache (모든 GPC가 공유)
```

**Command Processor(Front End)**는 CPU가 보낸 명령(커널 실행 요청)을 받아 GPC들에 파싱·분배하는 관문이다. **GPC(Graphics Processing Cluster)**는 TPC 여러 개를 묶은 큰 단위이고, **TPC(Texture Processing Cluster)**는 SM 여러 개를 묶은 단위다. 실제로 워프가 스케줄링되어 실행되는 물리적 코어 묶음은 결국 **SM**이다. 앞 절에서 "같은 스레드 블록에 속한 스레드는 하나의 SM 위에서 실행된다"고 한 문장이 가리키는 하드웨어가 바로 이 SM이다. GPU 드라이버는 그리드를 스레드 블록 단위로 쪼갠 뒤, 비어 있는 SM을 찾아 블록을 배치하고, SM은 그 블록을 다시 워프 단위로 잘라 스케줄링한다. GPC와 TPC는 이 수많은 SM을 물리적으로 묶어 배선과 캐시 공유 구조를 단순화하기 위한 상위 컨테이너다.

**L2 캐시**는 개별 SM에 속하지 않고 모든 GPC가 공유하는 자원이다. SM 안의 L1 캐시·공유 메모리보다 크지만 느리고, 그 아래의 글로벌 메모리(VRAM)보다는 훨씬 빠르다. 즉 메모리 계층에서 공유 메모리와 글로벌 메모리 사이에 L2 캐시라는 완충 계층이 하나 더 있는 셈이다. 이 부분은 뒤에서 메모리 계층을 다시 정리할 때 반영한다.

이 계층 구조의 세부 명칭은 회사마다 다르다.

| 구분 | 컨테이너 계층 | 실행/연산 유닛 | 특수 유닛 |
|------|--------------|---------------|-----------|
| NVIDIA(Ampere/Ada/Hopper) | GPC → TPC → SM | CUDA Core | Tensor Core, RT Core |
| AMD(RDNA 3) | Shader Engine → WGP(Work Group Processor) | CU(Compute Unit) | Vector ALU, Ray Accelerator |
| Intel(Arc Alchemist/Battlemage) | Render Slice | Xe Core(Vector Engine) | - |

이름은 회사마다 다르지만 뼈대는 같다. 큰 클러스터 안에 실행 유닛 묶음(SM/CU/Xe Core)이 여러 개 들어 있고, 그 묶음들이 캐시(L2 등)를 공유하며, 실제 스레드/워프 스케줄링은 그 실행 유닛 묶음 단위에서 일어난다.

## SM 내부 구성 — 워프 스케줄러와 CUDA Core, Tensor Core, SFU

SM 하나를 열어보면 워프 단위 실행을 뒷받침하는 구성 요소가 그대로 드러난다.

```
SM (Streaming Multiprocessor)
 ├─ 레지스터 파일(Register File)        스레드별 전용 저장 공간
 ├─ 워프 스케줄러 / 디스패처              어느 워프를 이번 사이클에 실행할지 결정
 ├─ Warp (32 스레드)                     스케줄러가 실행 대상으로 고르는 단위
 ├─ 실행 유닛(Execution Units)
 │   ├─ CUDA Core (FP32/INT32)          범용 산술 연산, 개수가 가장 많음
 │   ├─ Tensor Core (FP16/TF32/INT8 등) 행렬곱-누산(MAC) 전용, 딥러닝 가속
 │   └─ SFU(Special Function Unit)      sin/cos/exp 같은 특수 함수 전용
 ├─ L1 Cache / Texture Cache / Constant Cache   SM 내부 캐시
 └─ Shared Memory                       블록 단위 공유 메모리(L1 캐시와 물리적으로 같은 온칩 자원인 경우가 많음)
```

**워프 스케줄러**가 앞서 설명한 워프 실행의 실제 주체다. SM 안에는 보통 여러 워프가 동시에 상주하는데, 스케줄러는 매 사이클마다 그중 명령어를 실행할 준비가 된 워프를 골라 실행 유닛에 배정한다. 한 워프가 글로벌 메모리 접근으로 대기하는 동안 다른 워프를 실행시켜 유닛을 놀리지 않는 것이 이 스케줄러의 핵심 역할이다.

**실행 유닛은 하나가 아니라 세 종류로 나뉜다.** CUDA Core는 앞서 다룬 "단순한 산술 연산을 반복하는 코어"에 해당하고 개수가 가장 많다. Tensor Core는 행렬곱-누산(matrix multiply-accumulate)만 전담하는 특화 유닛으로, 딥러닝의 연산 대부분이 행렬곱이라는 점에 맞춰 등장했다. SFU(Special Function Unit)는 삼각함수·지수함수처럼 일반 ALU로 계산하면 여러 사이클이 걸리는 초월함수를 전용 회로로 빠르게 근사한다. 세 유닛이 역할을 나눠 맡기 때문에, 같은 SM 안에서도 행렬곱은 Tensor Core로, 일반 산술은 CUDA Core로 동시에 흘려보낼 수 있다.

**캐시도 용도별로 나뉜다.** L1 캐시는 일반적인 데이터 재사용을 위한 캐시이고, 텍스처 캐시는 텍스처 샘플링처럼 근접 좌표를 반복 조회하는 패턴에 최적화되어 있으며, 상수 캐시는 커널 실행 내내 값이 바뀌지 않는 상수 데이터를 읽기 전용으로 캐싱한다. 이 캐시들과 공유 메모리는 모두 SM 안에 물리적으로 올라간 온칩 자원이라는 공통점이 있다.

## 메모리 계층 — 레지스터, 공유 메모리, L2 캐시, 글로벌 메모리

코어가 수천 개라도 그 코어들이 데이터를 가져올 메모리가 느리면 아무 의미가 없다. GPU는 이 문제를 CPU와는 다른 방식으로 푼다. 접근 범위와 속도가 다른 메모리를 계층으로 나누고, 어떤 메모리를 쓸지를 상당 부분 개발자에게 맡긴다. 앞서 SM 내부 구조에서 다룬 L1 캐시·공유 메모리와 GPC 전체가 공유하는 L2 캐시를 더하면 계층은 다음처럼 네 단계로 정리된다.

| 메모리 | 접근 범위 | 속도 | 용량 | 비고 |
|--------|-----------|------|------|------|
| 레지스터(Register) | 스레드 1개 | 가장 빠름 | 스레드당 수십~수백 개 | 스레드 전용, 공유 불가 |
| 공유 메모리 / L1 캐시 | 블록 1개(블록 내 전 스레드) | 매우 빠름(온칩) | 블록당 수십~수백KB | 프로그래머가 직접 관리(공유 메모리) + 하드웨어 자동 관리(L1 캐시), SM 내부 |
| L2 캐시 | 칩 전체(모든 SM) | 빠름(온칩) | 수 MB~수십 MB | 모든 GPC/SM이 공유, 하드웨어가 자동 관리 |
| 글로벌 메모리(Global Memory) | 그리드 전체(모든 스레드) | 느림 | 수 GB~수십 GB(VRAM) | GPU 밖 DRAM(GDDR/HBM), [[semiconductor-chip-types-and-gpgpu|VRAM]]이 이 계층에 해당 |

레지스터는 스레드 하나에 배타적으로 할당되는 가장 빠른 저장 공간이다. 연산 중간값처럼 그 스레드만 쓰는 데이터를 담는다. 스레드 수가 워낙 많다 보니 스레드 하나가 쓸 수 있는 레지스터 수는 CPU 코어에 비해 훨씬 제한적이다.

공유 메모리는 같은 스레드 블록에 속한 스레드끼리 데이터를 주고받는 공간이다. SM 안에 물리적으로 올라가 있는 온칩(on-chip) 메모리라 글로벌 메모리보다 훨씬 빠르다. 다만 CPU 캐시처럼 하드웨어가 알아서 채우고 비우는 게 아니라, 개발자가 코드에서 명시적으로 값을 읽고 써야 한다. 그래서 "프로그래머가 관리하는 캐시"라 불린다. 같은 SM 안의 L1 캐시는 반대로 하드웨어가 자동으로 채우고 비우는 일반적인 캐시이며, 실제로는 공유 메모리와 같은 온칩 회로를 나눠 쓰는 경우가 많다. 행렬곱처럼 같은 데이터를 여러 스레드가 반복해서 읽는 연산에서 글로벌 메모리 접근을 공유 메모리 접근으로 바꾸는 것이 GPU 성능 최적화의 기본기다.

L2 캐시는 개별 SM 소속이 아니라 칩 전체, 즉 모든 GPC의 모든 SM이 공유하는 캐시다. SM 하나 안에서만 보이는 L1 캐시·공유 메모리보다는 접근 범위가 넓고 느리지만, SM 밖의 별도 칩인 글로벌 메모리보다는 훨씬 빠르다. 여러 SM이 같은 글로벌 메모리 영역을 반복해서 읽을 때, L2 캐시가 그 요청을 흡수해 VRAM까지 가는 트래픽을 줄여준다.

글로벌 메모리는 그리드 전체, 즉 모든 스레드 블록이 공통으로 접근하는 메모리다. GPU 카드에 꽂힌 VRAM이 바로 이 글로벌 메모리다. 용량은 가장 크지만 SM 밖에 있는 별도의 칩이라 접근 지연이 레지스터·공유 메모리·L2 캐시보다 훨씬 크다. 커널 하나가 글로벌 메모리에만 의존해서 데이터를 읽고 쓰면, 코어가 아무리 많아도 메모리 대역폭에 발목 잡힌다.

정리하면 레지스터는 스레드 개인 작업 공간, 공유 메모리/L1은 블록 단위 협업 공간, L2 캐시는 칩 전체가 공유하는 중간 완충 지대, 글로벌 메모리는 전체가 공유하는 창고다. 빠른 메모리일수록 좁은 범위에서만 보이고, 넓은 범위에서 보이는 메모리일수록 느리다는 트레이드오프는 CPU의 레지스터-캐시-메인 메모리 계층과 원리는 같다. 다만 GPU는 이 계층 관리를 하드웨어에만 맡기지 않고 개발자가 공유 메모리를 직접 다루게 열어뒀다는 점이 다르다.

## VGA(외장 그래픽)와 iGPU(내장 그래픽) — 같은 구조, 다른 배치

지금까지 다룬 GPC-TPC-SM 구조와 메모리 계층은 GPU 자체의 내부 구조다. 그런데 이 GPU가 시스템 안에서 CPU·메모리와 어떻게 배선되어 있느냐는 완전히 다른 문제이고, 여기서 VGA(외장 그래픽 카드)와 iGPU(내장 그래픽)의 차이가 갈린다.

**VGA(외장 그래픽 카드)**는 GPU가 자신만의 전용 VRAM(GDDR6X 등)을 옆에 두고, 256~384bit 폭의 고대역폭 인터페이스로 직결된다. CPU와는 별개의 칩이라 PCIe x16 버스를 통해 통신한다. 전용 메모리와 전용 냉각을 갖춘 만큼 TDP가 75W~600W 이상으로 높고, 그만큼 연산 성능도 높다. 고사양 게임, 3D 렌더링, AI/HPC처럼 메모리 대역폭과 연산량이 모두 큰 작업에 최적화되어 있다.

**iGPU(내장 그래픽)**는 GPU 코어가 CPU와 같은 패키지 안에 들어 있고, 전용 VRAM 없이 시스템 메모리(DDR4/DDR5)를 CPU와 나눠 쓴다. 이런 구조를 **UMA(Unified Memory Architecture, 통합 메모리 아키텍처)**라 부른다. CPU와 동일 패키지에 있고 LLC(Last Level Cache)도 공유하기 때문에 지연 시간과 전력 효율이 좋지만, 시스템 메모리의 대역폭이 VRAM보다 낮아 연산 성능은 제한적이다. TDP가 10W~65W로 낮아 냉각 부담이 적고, 사무용·영상 출력·경량 게임·미디어 가속처럼 대역폭보다 전력 효율이 중요한 용도에 적합하다.

| 항목 | VGA(외장 그래픽) | iGPU(내장 그래픽) |
|------|------------------|--------------------|
| 메모리 | 전용 VRAM(GDDR6X 등) | 시스템 메모리 공유(DDR, UMA) |
| 메모리 대역폭 | 높음(256~384bit) | 상대적으로 낮음 |
| 연산 성능 | 매우 높음(많은 SM, 높은 클럭) | 상대적으로 낮음(전력 제약) |
| 전력 소비(TDP) | 높음(75W~600W+) | 낮음(10W~65W) |
| 지연 시간 | PCIe 통신으로 인한 추가 지연 | CPU와 동일 다이/패키지, 낮은 지연 |
| 주요 용도 | 고사양 게임, 3D 렌더링, AI, HPC | 일반 작업, 영상 출력, 경량 게임, 미디어 가속 |
| 업그레이드 | 가능(카드 교체) | 불가능(CPU 교체 필요) |

즉 VGA와 iGPU는 GPC-TPC-SM이라는 GPU 내부 구조 자체가 다른 게 아니라, 그 GPU가 전용 메모리를 갖고 별도 칩으로 존재하느냐(VGA), CPU와 메모리를 공유하며 한 패키지에 통합되어 있느냐(iGPU)의 차이다. 이는 앞서 정리한 지연시간 최소화 vs 처리량 극대화라는 CPU-GPU 설계 목표의 축소판이기도 하다. iGPU는 저전력·저지연 쪽으로, VGA는 처리량 극대화 쪽으로 더 치우쳐 설계된다.

## 그래서 GPGPU는 이 구조 위에서 동작한다

[[semiconductor-chip-types-and-gpgpu|이전 미션]]에서 GPGPU는 GPU의 병렬 연산 구조를 그래픽 밖으로 확장하는 개념이라고 정리했다. 이제 그 구조가 정확히 무엇인지 채울 수 있다. 단순한 ALU 수천 개, 그 코어들을 32개씩 묶어 같은 명령어를 동시에 실행시키는 SIMT 모델, 스레드-블록-그리드로 이어지는 실행 계층, 그리고 레지스터-공유 메모리-글로벌 메모리로 이어지는 메모리 계층. 이 네 가지가 맞물려 GPU를 "동일한 연산을 대량의 데이터에 반복 적용하는 작업"에 특화된 하드웨어로 만든다.

딥러닝의 행렬곱이 정확히 이 모양이다. 행렬의 원소 하나하나를 계산하는 연산은 단순하고 서로 독립적이다. 원소 하나를 스레드 하나에 매핑하면 수백만 개의 독립적인 스레드가 생기고, 이 스레드들을 워프 단위로 묶어 SM에 뿌리면 코어 수천 개가 동시에 돌아간다. CUDA, OpenCL 같은 프레임워크는 결국 이 매핑, 즉 "내 연산을 스레드 계층에 어떻게 나눠 담을 것인가"를 개발자가 다룰 수 있게 만든 도구다.

## 핵심 정리

- CPU는 제어 로직과 캐시에, GPU는 ALU에 다이 면적을 집중한다. CPU는 지연시간 최소화, GPU는 처리량 극대화라는 서로 다른 목표 때문이다.
- GPU는 SIMT(Single Instruction, Multiple Thread) 모델로 코어 수천 개를 관리한다. 스레드 32개를 워프로 묶어 같은 명령어를 락스텝으로 실행한다.
- 워프 안에서 분기가 갈리면(Warp Divergence) 경로를 순차적으로 실행해야 해서 처리량이 떨어진다.
- 실행 단위는 스레드 → 스레드 블록 → 그리드로 쌓이고, 하드웨어는 이를 워프 단위로 잘라 SM에서 스케줄링한다.
- 메모리는 레지스터(스레드 전용) → 공유 메모리(블록 단위, 온칩) → 글로벌 메모리(그리드 전체, VRAM) 순으로 범위가 넓어지고 속도는 느려진다.
- GPGPU는 이 구조, 즉 단순 코어의 대량 병렬 실행과 계층적 메모리를 그래픽 밖의 범용 연산(딥러닝 등)에 그대로 활용하는 것이다.

작전명 AI, 코드네임 23의 세번째 미션은 여기까지다. GPU가 왜 병렬 연산에 강한지를 다이 구조, 실행 모델, 메모리 계층 세 층위에서 뜯어봤다면 이번 미션도 완료된 셈이다.
