# SQL 날짜 조회 최적화 — Sargable, Range Scan, BETWEEN 함정

_written by Claude-Code_

## 배경: 어떤 조건절이 맞을까?

특정 연도의 데이터만 조회하는 쿼리를 작성하다 보면 머릿속에 몇 가지 방법이 동시에 떠오른다.

```sql
WHERE YEAR(created_at) = 2025

WHERE created_at >= '2025-01-01' AND created_at < '2026-01-01'

WHERE created_at BETWEEN '2025-01-01' AND '2025-12-31'
```

세 쿼리는 모두 "2025년 데이터를 가져온다"는 같은 목적을 가진다. 하지만 실행 계획도, 때로는 결과로 나오는 행의 개수도 달라질 수 있다. 어떤 조건을 선택해야 인덱스를 제대로 활용하면서 정확한 결과를 얻을 수 있을까? 이 질문에 답하려면 먼저 인덱스가 데이터를 어떤 방식으로 찾아내는지부터 살펴봐야 한다.

![인덱스를 제대로 사용하는 SQL 작성법|860](/assets/posts/data/sql-date-range-query-optimization/sql-sargable-range-scan.png)

## B-Tree 인덱스, 정렬된 구조 위에서 찾는다

대부분의 RDBMS는 인덱스를 B-Tree 구조로 저장한다. B-Tree는 키 값을 정렬된 상태로 유지하면서 트리 형태로 분기하는 자료구조다. 루트 노드에서 출발해 리프 노드까지 내려가는 동안, 찾으려는 값의 위치를 단계적으로 좁혀나간다.

여기서 짚고 넘어가야 할 전제가 하나 있다. **인덱스는 컬럼의 "원본 값"이 정렬되어 있다는 것을 바탕으로 동작한다.** WHERE 절의 조건이 이 정렬 순서를 그대로 활용할 수 있는 형태일 때만 인덱스가 제 역할을 한다. 조건이 이 전제를 깨뜨리는 순간 옵티마이저는 인덱스를 포기하고 풀 스캔으로 돌아선다.

이 전제가 유지되는지 아닌지를 가르는 기준이 바로 Sargable이다.

## Sargable 조건 — 인덱스를 탈 수 있는가의 분기점

Sargable은 Search ARGument ABLE의 줄임말로, 쿼리 조건이 인덱스를 활용할 수 있는 형태인지를 가리키는 용어다. 같은 결과를 의도한 조건이라도 작성 방식에 따라 Sargable이 될 수도, Non-Sargable이 될 수도 있다.

```sql
-- Non-Sargable: 컬럼에 함수를 적용
WHERE YEAR(created_at) = 2025

-- Sargable: 컬럼은 그대로, 비교값만 가공
WHERE created_at >= '2025-01-01' AND created_at < '2026-01-01'
```

`YEAR(created_at) = 2025`는 직관적으로 보이지만 인덱스 입장에서는 문제가 생긴다. 인덱스에는 `created_at`의 원본 값이 정렬되어 저장되어 있는데, 비교를 수행하기 전에 매번 `YEAR()`라는 함수를 거쳐야 하기 때문이다. 정렬되어 있는 것은 `created_at` 원본 값이지, `YEAR(created_at)`로 변환한 결과값이 아니다. 결국 인덱스가 가진 정렬 순서를 그대로 따라갈 수 없게 되고, 옵티마이저는 모든 행을 읽어 함수를 적용한 뒤 비교하는 풀 스캔을 선택한다.

반대로 `created_at >= '2025-01-01' AND created_at < '2026-01-01'`은 컬럼 자체를 가공하지 않는다. 변형이 가해지는 쪽은 비교 대상이 되는 리터럴 값이고, 컬럼은 원본 그대로 비교에 참여한다. 이 형태라면 인덱스에 저장된 정렬 순서를 그대로 따라가며 범위를 찾을 수 있다.

정리하면, **컬럼을 함수나 연산으로 감싸는 순간 인덱스는 무효화되고, 컬럼은 그대로 둔 채 비교값 쪽에서 범위를 조정하면 인덱스를 그대로 활용할 수 있다.** 같은 의도를 표현하더라도 변형을 어느 쪽에 가하느냐가 실행 계획을 가른다.

## Range Scan — 정렬된 구조이기에 가능한 탐색

Sargable한 조건이 주어지면 B-Tree 인덱스는 Range Scan(범위 스캔) 방식으로 데이터를 찾는다. 이는 인덱스가 정렬되어 있기 때문에 가능한 동작이다.

`created_at >= '2025-01-01' AND created_at < '2026-01-01'` 같은 조건이 들어오면, 옵티마이저는 정렬된 인덱스에서 `'2025-01-01'`에 해당하는 위치를 먼저 찾는다. 이후로는 조건을 만족하지 않는 지점(`'2026-01-01'`)이 나타날 때까지 순서대로 읽기만 하면 된다. 시작점을 찾는 데는 트리 구조를 타고 내려가는 탐색 비용이 들지만, 그다음부터는 정렬된 순서를 따라가는 순차 접근이라 비용이 크게 줄어든다.

이것이 부등호 조건(`>=`, `<`)이 인덱스와 잘 맞는 이유다. 부등호는 "어디서부터 어디까지"라는 범위를 명확하게 정의하고, B-Tree는 그 범위의 시작점과 끝점을 정렬된 구조 위에서 효율적으로 짚어낼 수 있다.

## BETWEEN의 함정 — Inclusive 경계가 만드는 누락

세 번째로 떠올릴 수 있는 방법이 BETWEEN이다.

```sql
WHERE created_at BETWEEN '2025-01-01' AND '2025-12-31'
```

BETWEEN은 Sargable하고 Range Scan도 그대로 활용할 수 있다는 점에서는 문제가 없다. 함정은 다른 곳에 있다. **BETWEEN은 양쪽 경계를 모두 포함(inclusive)하는 연산자다.**

`created_at`의 타입이 DATETIME이라고 가정해보자. `'2025-12-31'`이라는 값은 실제로는 `'2025-12-31 00:00:00'`으로 해석된다. 따라서 위 조건은 사실상 `created_at <= '2025-12-31 00:00:00'`과 동일하게 동작하고, `'2025-12-31 09:30:00'`이나 `'2025-12-31 23:59:59'` 같은 값은 조건을 만족하지 못해 결과에서 빠진다. 분명히 2025년에 속하는 데이터인데도 누락되는 셈이다.

이 문제를 피하는 방법은 명확하다. 끝나는 지점을 "포함"이 아니라 "다음 경계의 시작 직전"으로 표현하는 것이다.

```sql
WHERE created_at >= '2025-01-01 00:00:00'
  AND created_at <  '2026-01-01 00:00:00'
```

시작은 포함(`>=`)하고 끝은 제외(`<`)하는 이 형태를 Half-Open Interval(반열린 구간)이라고 부른다. 날짜나 시간처럼 연속된 값을 다루는 범위 조건에서는 BETWEEN보다 이 패턴이 더 안전하다. 경계에 어떤 시각 값이 들어오더라도 누락되거나 중복으로 집계될 가능성이 없기 때문이다.

## 정리

세 개념은 하나의 흐름으로 연결된다.

- **B-Tree 인덱스**는 컬럼의 원본 값을 정렬된 상태로 유지한다.
- **Sargable**은 이 정렬 순서를 깨뜨리지 않는 조건인지를 가르는 기준이다. 컬럼에 함수를 적용하면 정렬 순서를 활용할 수 없고, 컬럼은 그대로 둔 채 비교값만 조정하면 정렬 순서를 그대로 따라갈 수 있다.
- **Range Scan**은 Sargable한 부등호 조건이 주어졌을 때, 정렬된 인덱스에서 시작점을 찾고 그 뒤를 순차적으로 읽어나가는 동작이다.
- **BETWEEN**은 Sargable하지만 양쪽 경계를 포함하는 inclusive 특성 때문에, DATETIME처럼 연속된 값을 다룰 때는 의도하지 않은 누락을 만들 수 있다. 이때는 시작은 포함하고 끝은 제외하는 Half-Open Interval 형태가 더 안전하다.

결국 "특정 연도의 데이터를 조회한다"는 같은 목표 앞에서, `created_at >= '2025-01-01' AND created_at < '2026-01-01'` 형태가 인덱스 활용과 정확성 두 가지를 모두 만족시키는 선택이 된다. 컬럼은 건드리지 않고, 비교값으로 범위를 명확히 표현하며, 경계는 반열린 구간으로 정의하는 것 — 이 세 가지가 날짜 범위 조회를 작성할 때 기억해야 할 핵심이다.
