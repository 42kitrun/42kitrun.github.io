# 유스케이스 다이어그램으로 에이전트 요구사항 정의하기

_written by Claude-Code, ChatGPT_

[[uml-for-ai-agent-intro|UML 시리즈 1편]]에서 다뤘듯이, UML 다이어그램은 AI Agent 개발의 각 단계에서 설계를 구조화하는 도구다. 이번 편은 그 시작점인 유스케이스 다이어그램이다.

## 유스케이스 다이어그램이란

유스케이스 다이어그램은 **시스템이 외부 사용자(액터)에게 제공하는 기능과, 사용자가 달성하고자 하는 목표(유스케이스)를 상위 수준에서 표현하는 UML 다이어그램**이다.

핵심 목적은 세 가지다:
- 시스템의 **기능 범위** 정의
- **사용자 관점**의 요구사항 정리
- 이해관계자 간 **공통 언어** 제공

---

## AI Agent 개발에서 왜 중요한가

AI Agent는 자연어로 요구사항이 들어오는 특성이 있다. "고객 문의에 자동으로 답변해줘"라는 한 문장 안에는 수십 개의 기능이 숨어 있다. 유스케이스 다이어그램은 이 자연어 요구사항을 구조화해서 기능 누락과 중복을 방지한다.

구체적으로 네 가지 역할을 한다:

1. **자연어 요구사항 구조화** — 기능 누락과 중복 사전 예방
2. **사용자 가치 중심 범위 설정** — AI Agent의 목표와 경계를 명확히
3. **설계 기준선(Requirements Baseline) 제공** — 이후 시퀀스, 클래스, 상태, 컴포넌트 다이어그램 작성의 출발점
4. **이해관계자 소통 도구** — 비개발자 포함 모든 관계자가 이해할 수 있는 언어로 표현

## 구성 요소

| 구성 요소 | 설명 |
|-----------|------|
| **액터 (Actor)** | 시스템과 상호작용하는 외부 사용자 또는 외부 시스템 |
| **유스케이스 (Use Case)** | 액터가 달성하고자 하는 목표 (시스템이 제공하는 기능) |
| **시스템 경계 (System Boundary)** | 시스템의 범위를 구분하는 경계선(스코프) |
| **연관 (Association)** | 액터와 유스케이스의 상호작용 |
| **포함 `<<include>>`** | 공통으로 재사용되는 하위 기능 |
| **확장 `<<extend>>`** | 선택적/조건부로 추가되는 기능 |
| **일반화 (Generalization)** | 상위 유스케이스를 상속받는 관계 |

AI Agent에서 액터는 사람 사용자에 한정되지 않는다. 캘린더, 이메일 서비스, CRM처럼 에이전트와 연동하는 외부 시스템도 액터다.

## 예시 1: 지능형 고객지원 에이전트

고객지원 AI Agent를 유스케이스로 표현하면 다음과 같다.

**액터**: 고객, 상담사, 관리자, 외부 시스템(CRM)

| 유스케이스 | 관계 |
|------------|------|
| 질문하기 | 고객 → 에이전트 |
| 답변 받기 | 고객 ← 에이전트 |
| 답변 평가하기 | 질문하기에서 `<<extend>>` |
| 추가 정보 요청 | 답변 받기에서 `<<extend>>` |
| 상담 이력 확인 | 상담사 → 에이전트 (`<<include>>` 고객 정보 조회) |
| 지식 베이스 관리 | 외부 시스템(CRM) → 에이전트 |

이 다이어그램 하나로 다음이 명확해진다:
- 에이전트가 처리해야 할 모든 상호작용의 목록
- 각 기능이 어느 액터와 연결되는지
- `<<include>>`로 공통 기능 재사용 구조
- `<<extend>>`로 선택적 흐름 분리

## 예시 2: 개인 비서 AI Agent

외부 시스템과 연동이 많은 개인 비서 에이전트 예시다.

**액터**: 사용자, 캘린더(외부 시스템), 이메일 서비스(외부 시스템), 알림 서비스(외부 시스템)

```
사용자
├── 일정 조회
├── 일정 등록 ──<<include>>── 시간 충돌 확인 ← 캘린더
├── 이메일 요약 ──<<include>>── 이메일 수신 ← 이메일 서비스
├── 할 일 관리 ──<<extend>>── 우선순위 설정
├── 정보 검색
└── 알림 설정 ← 알림 서비스
```

"일정 등록" 시 "시간 충돌 확인"은 항상 필요하므로 `<<include>>`, "할 일 관리"에서 "우선순위 설정"은 사용자 선택이므로 `<<extend>>`다.

## 요구사항 정의 5단계

유스케이스 다이어그램을 완성한 후에는 실제 요구사항 명세로 구체화해야 한다.

### 1단계: 유스케이스 선정

핵심 가치를 제공하는 주요 유스케이스를 선택한다. 예: 답변 받기, 질문하기, 상담 이력 확인

### 2단계: 시나리오 정의

각 유스케이스의 기본 흐름과 예외 흐름을 구체적으로 작성한다.

"답변 받기" 기본 흐름 예시:
1. 고객이 질문을 입력한다
2. 에이전트가 의도를 파악한다
3. 지식 베이스/외부 출처를 검색한다
4. 근거를 바탕으로 답변을 생성한다
5. 고객에게 답변을 제공한다

### 3단계: 기능 요구사항 도출

시나리오를 구현하기 위한 기능을 목록화한다.

- 의도 파악 (NLU)
- 지식 검색 (RAG)
- 답변 생성 (LLM)
- 출처/근거 제시
- 피드백 수집

### 4단계: 비기능 요구사항 정의

품질, 성능, 보안 등 제약과 기준을 정의한다.

- 응답 시간: 평균 3초 이내
- 정확도: Top-1 기준 85% 이상
- 가용성: 99.5% 이상
- 개인정보보호 및 보안 준수
- 로그/모니터링 및 추적 가능성

### 5단계: 검증 및 우선순위

가치/노력 기준으로 우선순위를 부여하고 MVP 범위를 확정한다.

| 구분 | 설명 |
|------|------|
| Quick Win | 가치 높고 노력 낮음 — 먼저 구현 |
| Strategic | 가치 높고 노력 높음 — 핵심 기능 |
| Fill-in | 가치 낮고 노력 낮음 — 여유 있을 때 |
| Reconsider | 가치 낮고 노력 높음 — 재검토 |

## 유스케이스 작성 시 주의사항

**시스템 경계를 명확히 한다** — 무엇이 시스템 내부이고 외부인지 구분한다.

**사용자의 목표를 표현한다** — "리포트를 생성한다"가 아니라 "사용자가 리포트를 생성한다"처럼 주체를 사용자로 둔다. 구현 행동이 아닌 목표 관점으로 쓴다.

**너무 세분화하지 않는다** — "주문 데이터 파싱", "캐시 조회"는 유스케이스가 아니다. 사용자 관점에서 의미 있는 단위로 유지한다.

**`<<include>>`와 `<<extend>>` 구분** — `<<include>>`는 항상 실행되는 공통 기능, `<<extend>>`는 조건부로 실행되는 선택 흐름이다.

## 산출물 체크리스트

```
[ ] 유스케이스 다이어그램 (범위 정의)
[ ] 유스케이스 명세서 (시나리오/규칙)
[ ] 요구사항 명세서 (FR / NFR)
[ ] 우선순위 백로그 (MVP 계획)

[ ] 모든 주요 액터와 이해관계자가 검토했는가?
[ ] 유스케이스의 경계(포함/제외)가 명확한가?
[ ] 각 유스케이스에 기본/예외 시나리오가 있는가?
[ ] 기능 요구사항이 테스트 가능한 수준으로 작성되었는가?
[ ] 비기능 요구사항의 측정 기준이 구체적인가?
[ ] 우선순위와 MVP 범위가 합의되었는가?
```

## AI Agent 개발 흐름에서의 위치

유스케이스 다이어그램은 전체 UML 설계 흐름의 첫 번째 단계다.

```
요구사항 수집 (자연어, 인터뷰, 문서)
        ↓
유스케이스 다이어그램 (요구사항 정의) ← 지금 여기
        ↓
시퀀스 다이어그램 (흐름 설계)
        ↓
클래스 다이어그램 (데이터 모델링)
        ↓
상태 다이어그램 (상태 전환)
        ↓
컴포넌트 다이어그램 (아키텍처)
```

유스케이스 다이어그램으로 '무엇을' 제공할지 지도화하고, 요구사항 정의로 '어떻게' 만들지 구체화하면 이후 모든 설계가 일관성을 유지할 수 있다.
